Expense Manager

📌 What is this project?

A full-stack expense tracking system where:

  • Users manage expenses in a web UI
  • Backend handles authentication, storage, and business logic
  • Runs in both local development and production environments
  • Infrastructure is fully containerized with Docker

Prerequisites

  • Git
  • Docker (version 20+)
  • Docker Compose (v2+)
  • No need to install Java, Node.js, PostgreSQL, or anything else locally.

Features

  • User registration, login, and account management
  • Add, edit, delete, and view expenses
  • Basic report generation
  • File upload support
  • Real-time updates using WebSocket

Backend

The backend is built with Spring Boot. Here are some things I implemented:

  • Liquibase for database schema updates and versioning
  • Spring Data JPA + Hibernate for database operations
  • JWT for authentication and authorization
  • RabbitMQ for background processing
  • Rate Limiting on important endpoints
  • Spring Actuator for basic monitoring
  • Access logs enabled via Tomcat
  • Caching using Spring Cache + Caffeine (in-memory)

Testing

Applied testing strategy across different backend layers :

  • Controller Layer: Tested using @WebMvcTest and MockMvc (with addFilters = false to isolate Spring MVC controllers from security filters).
  • Service Layer: Isolated unit testing using JUnit 5 and Mockito for core business logic.
  • Repository Layer: Database slice testing using @DataJpaTest powered by Testcontainers for real PostgreSQL container execution.
  • Security & Filters: Integration tests verifying the custom JWT filter and Rate Limiting filter within the Spring Security filter chain.

Frontend

The frontend is a React application built with Vite that provides the user interface for interacting with the expense management api.

  • Built with React and Vite
  • Communicates with the Spring Boot REST API using HTTP requests
  • Handles JWT-based authentication on the client side
  • Uses React Router for client-side navigation
  • Uses TanStack Query for server-state management and API data fetching
  • Uses WebSocket communication to receive expense report generation results in real time

Environment Configuration

Backend Spring Profiles

The backend uses three configuration files:

  • application.yml — Common settings (applies to all profiles)
  • application-dev.yml — Development settings (detailed logs, full actuator, etc.)
  • application-prod.yml — Production settings (optimized pool, minimal logs, secure)

Deployment & Infrastructure

The application is fully containerized using Docker and Docker Compose. The production environment is deployed on AWS EC2, with GitHub Actions used for continuous integration and deployment.

Docker

  • Backend, frontend, PostgreSQL, and RabbitMQ run as Docker services. Health checks are made before allowing container creation and we use named volumes to persist data generated from db and rabbit containers
  • Docker Compose manages the application stack and defines a docker network
  • Frontend uses a multi-stage Docker build for creating the nginx final image which acts as reverse proxy and entry point of backend server and serves frontend files and proxy requests to springboot server.

CI/CD

Automated via Github Actions with path-filtering and conditionals to selectively run only affected components, backend or frontend.

  • Filtering & Control: File-change detection job determine what is modified, and conditional statements (if checks) skip unchanged build jobs.
  • Testing: Executes JUnit tests for the backend.
  • Registry Push: Authenticates with Docker Hub and pushes updated images to production on every push to main.
  • Secure Delivery: Uploads required deployment process files (docker-compose.yml, config.alloy) to an S3 bucket and triggers remote execution on EC2 via AWS Systems Manager (SSM).

AWS Infrastructure

AWS services are used to support the deployment process and provide the required infrastructure.

  • EC2: Hosts the production application and runs the Docker Compose stack.
  • IAM: Provides separate roles and permissions for GitHub Actions and the EC2 instance.
  • GitHub OIDC: Allows GitHub Actions to authenticate with AWS without storing long-lived AWS credentials.
  • Systems Manager (SSM): GitHub Actions uses SSM to send deployment commands to the EC2 instance.
  • S3: Provides storage used by the deployment infrastructure.

The GitHub Actions IAM role is configured with the permissions required for the deployment workflow, while the EC2 instance uses its own IAM role for the AWS resources required by the application and deployment process.

Deployment flow:

      ↓
GitHub OIDC
      ↓

      ↓
AWS Systems Manager (SSM)
      ↓

      ↓

      ↓

Running the Application

Option 1: Full Docker Setup (Local)

Runs the complete application stack using Docker:

  • Frontend (React + Nginx)
  • Spring Boot Backend
  • PostgreSQL
  • RabbitMQ
git clone https://github.com/Nikos32-ux/Expense-manager-app.git
cd Expense-manager-app
docker compose up --build

Access:

  • Frontend → http://localhost
  • Backend API → http://localhost:8080

Uses:

  • .env.prod
  • application-prod.yml

Option 2: Local Development Setup

Runs the backend from IntelliJ and the frontend from the Vite development server.

Start infrastructure services:

docker compose up -d postgres rabbitmq

Then in IntelliJ Run Configuration, add these variables:

SPRING_PROFILES_ACTIVE=dev
SPRING_DATASOURCE_URL=jdbc:postgresql://:/
SPRING_DATASOURCE_USERNAME=your_db_name
SPRING_DATASOURCE_PASSWORD=your_secure_password_here
JWT_SECRET=your_strong_jwt_secret_here
CLOUDINARY_CLOUD_NAME=your_cloudinary_cloud_name
CLOUDINARY_API_KEY=your_cloudinary_api_key
CLOUDINARY_API_SECRET=your_cloudinary_api_secret

Run the backend from IntelliJ

Option 3: Production (AWS EC2)

Same Docker setup, deployed on server.

docker compose up -d --build

Uses:

  • .env.prod
  • same Spring profile as Docker mode

API Documentation

The backend provides API documentation using Swagger UI and OpenAPI.

When running the application locally, Swagger UI is available at: 

http://localhost:8080/swagger-ui/index.html

Swagger UI allows you to:

  • View available API endpoints
  • Inspect request parameters, request bodies, and responses
  • Register a user through the authentication endpoint
  • Log in to obtain a JWT
  • Use the JWT to authenticate requests to protected endpoints
  • Send requests directly from Swagger UI using Try it out

To test protected endpoints, first register a user and log in to obtain a JWT.
